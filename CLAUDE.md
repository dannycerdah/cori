# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Clínica Cori is a Laravel 10 + Livewire 4 web app for a medical clinic: a public marketing site (home, nosotros, contacto, citas) plus a small authenticated admin panel for managing appointments and patients. No SPA framework — pages are server-rendered Blade with Livewire components for interactivity. Built to deploy on cPanel without a Node.js runtime in production (assets are pre-built with Vite and committed/uploaded, not built server-side).

## Commands

```bash
# Install PHP deps
composer install

# Env setup (first time)
cp .env.example .env
php artisan key:generate

# DB: fresh schema + seed data (specialties, hero, services, admin user, etc.)
php artisan migrate:fresh --seed

# Dev server
php artisan serve            # http://127.0.0.1:8000

# Frontend assets (only needed when editing resources/css or resources/js)
npm install
npm run dev                  # Vite dev server
npm run build                # production build, output committed for cPanel deploy

# Tests (PHPUnit, not Pest)
php artisan test
php artisan test --filter=TestName
vendor/bin/phpunit tests/Feature/ExampleTest.php

# Code style
vendor/bin/pint              # Laravel Pint, fixes in place
vendor/bin/pint --test       # check only

# Tinker (for one-off DB inspection instead of throwaway PHP scripts)
php artisan tinker
```

Default admin login (seeded via `AdminUserSeeder`): `admin@clinicacori.com` / `password123`.

**`DatabaseSeeder::run()` must call every seeder needed for a working install** (`AdminUserSeeder`, `EspecialidadesSeeder`, `ServicioSeeder`, `DoctorSeeder`, `HorarioSeeder`, `ServiceSeeder`, `SurgerySeeder`, `EcografiaSeeder`, `HeroSeeder`, `ContentSectionSeeder`, `ContactInfoSeeder`) — it used to call only three of them, so a clean `migrate:fresh --seed` produced zero users (nobody could log into `/admin`) and no Hero/Ecografía/ContentSection content. Note `ServicioSeeder` (bookable services per specialty) is distinct from `ServiceSeeder` (English `services` table, marketing content). `HeroSeeder` and `ContactInfoSeeder` are currently empty stubs (harmless no-ops kept for future use — the `Hero` component falls back to hardcoded copy when no active `Hero` row exists, and `ContactInfo` is a model/table with no code reference anywhere, superseded by `ContentSection`'s `contact_*` keys). If you add real seed data to either, `DatabaseSeeder` already calls them so it'll take effect automatically.

## Architecture

**Routing is controller-based, not Livewire full-page.** All routes live in `routes/web.php` and dispatch to plain controllers (`HomeController`, `AuthController`, `Admin\CitaController`) that return Blade views. Livewire is used only for islands of interactivity embedded inside those views (the appointment form, the hero/services/etc. sections on the homepage), not for routing.

**All Livewire components live in `app/Livewire` (namespace `App\Livewire`)**: `Contact`, `Hero`, `Ecografias`, `Especialidades`, `Services`, `Surgeries` (resolved via tag auto-discovery, e.g. `<livewire:hero />`), `CitaForm` (referenced explicitly as `@livewire(\App\Livewire\CitaForm::class)` in `citas.blade.php` and `home.blade.php`), and `AdminCitas` (referenced by string as `@livewire('admin-citas')` in `admin/citas/index.blade.php`, rendering `resources/views/livewire/admin-citas.blade.php`). The admin CRUD managers live under `app/Livewire/Admin` (namespace `App\Livewire\Admin`): `EspecialidadesManager`, `ServiciosManager`, `DoctoresManager`, `HorariosManager`, `BloqueosManager` — each referenced by string as `@livewire('admin.especialidades-manager')` etc. from its host view `admin/<entity>/index.blade.php`, rendering `resources/views/livewire/admin/<entity>-manager.blade.php`. There used to be a parallel `app/Http/Livewire` namespace with stale duplicates of the first six components — dead code left over from a Livewire v2→v3 migration — it was removed. **When checking whether a Livewire component is actually referenced, grep for all three call styles**: `<livewire:kebab-name`, `@livewire(Fully\Qualified\Class::class)`, and `@livewire('kebab-name')` — the string form doesn't match a class-name search and caused `AdminCitas` to be misidentified as dead code once.

**Admin CRUD manager pattern** (`app/Livewire/Admin/*Manager.php` + `resources/views/livewire/admin/*-manager.blade.php`): each entity gets one plain controller (`Admin\<Entity>Controller@index` returning a host Blade view) plus one Livewire "manager" component that owns the list *and* the create/edit/delete/toggle-estado actions — no extra routes. Managers use `WithPagination` + `paginationTheme = 'tailwind'`, form props + `$editandoId` + `$mostrarModal`, `abrirModal()`/`editar($id)`/`cerrarModal()`/`guardar()`/`eliminar($id)`/`toggleEstado($id)`, `rules()`/`messages()` (Spanish), `updating<Filtro>()` → `resetPage()`, and `session()->flash('message'|'error', …)`. The modal is a server-rendered `@if($mostrarModal)` overlay with Alpine only for `x-on:keydown.escape.window="$wire.cerrarModal()"` and a `wire:click="cerrarModal"` backdrop — no separate Alpine `<script>` (Livewire 4 bundles Alpine). `eliminar()` refuses to hard-delete a row that still has dependents (`withCount` guard) and tells the user to deactivate it instead. Follow this pattern for any new admin entity.

**Core domain models** (`app/Models`): `Paciente` (patient, keyed by `tipo_documento` + `numero_documento` — DNI/CE; name is split into `nombres` + `apellidos`, with a `nombre_completo` accessor; contact field is `correo`, not `email`; has a `estado` boolean), `Especialidad` (medical specialty; `estado` boolean — was `activo`), `Servicio` (bookable service belonging to an `Especialidad`, `requiere_doctor` flag — **not** the marketing `Service`/`services` model), `Doctor` (`doctores` table, `nombres`/`apellidos` + `nombre_completo` accessor, `belongsToMany(Especialidad, 'doctor_especialidades')`), `Horario` (availability template: `belongsTo` `Servicio` + optional `Doctor`, `hora_inicio`/`hora_fin`/`frecuencia_minutos`/`capacidad`, optional `fecha_inicio`/`fecha_fin` validity window — both null = permanent, e.g. a doctor who only works 01/01/2027–29/01/2027 — `hasMany(HorarioDia)` for weekdays 1–7 ISO), `HorarioDia`, `BloqueoHorario` (`bloqueos_horario` table, doctor unavailability windows). `Cita` (appointment; `belongsTo` `Paciente`, `Especialidad`, `Servicio`, optional `Doctor`/`Horario`; `fecha` + `hora_inicio`/`hora_fin`; `tipo` is `NORMAL`/`EXCEPCIONAL`; `estado` is one of `REGISTRADA`/`CONFIRMADA`/`ATENDIDA`/`CANCELADA`/`NO_ASISTIO`; free-text `observacion`). Content/CMS-ish models feeding the public site: `Hero`, `Service`, `Ecografia`, `Surgery`, `ContentSection` (generic key/value content blocks, see `Contact` component's use of keys like `contact_address`), `ContactInfo`.

**The schema was rebuilt** (`migrate:fresh` only, no data preserved): the `create_especialidades`/`create_pacientes`/`create_citas` migrations were edited in place, the old `add_activo_*`/`add_document_fields_*` migrations deleted, and new `create` migrations added for `servicios`, `doctores`, `doctor_especialidades`, `horarios`, `horario_dias`, `bloqueos_horario` (timestamped between pacientes and citas so FKs resolve; citas moved to `..._225610`). MySQL `CHECK` constraints from the source DDL are expressed as Laravel `enum()` columns (`citas.tipo`/`citas.estado`) or enforced in Livewire validation (`hora_fin` `after:hora_inicio`, `dias_semana` `between:1,7`, `min:1` on counts) since Laravel 10's schema builder has no fluent `->check()`.

**Appointment booking goes through `App\Livewire\CitaForm::reservar`** (Livewire form with live patient lookup via `buscarPaciente`/`updated`), which validates, upserts the `Paciente` (keyed on document type+number, writing `nombres`/`apellidos`/`correo`) and creates the `Cita` (`estado = REGISTRADA`, `tipo = NORMAL`) inside a `DB::transaction`. The form has a `servicio_id` select that depends on the chosen `especialidad_id` (both `wire:model.live`, `getServiciosProperty()` reloads active services). The old `notas` field is now `observacion`.

**Availability is computed from the service's `horarios`** — patients no longer type a free date/time. `App\Support\DisponibilidadCitas` (`fechasDisponibles($servicio)`, `slotsDisponibles($servicio, $fecha)`, `slotSigueDisponible(...)`) generates candidate slots for the next `CitaForm::DIAS_VENTANA` (15) days from each active `Horario` (`hora_inicio`→`hora_fin` stepped by `frecuencia_minutos`, only on its `horario_dias` weekdays, within its `fecha_inicio`/`fecha_fin` window), drops slots at/over `capacidad` (counting non-`CANCELADA`/`NO_ASISTIO` citas for that service+date+start), drops past times today, and drops slots overlapping an active `BloqueoHorario` for the slot's doctor. `CitaForm` exposes `fechasDisponibles`/`slotsDisponibles` computed props (memoized per request — both partials render them) and `elegirFecha()`/`elegirHora()` actions; the `disponibilidad.blade.php` partial (included by both `escritorio` and `movil`) renders date chips then time-slot buttons. `reservar()` re-checks the slot via `slotSigueDisponible()` and again with a `lockForUpdate` count inside the transaction, and stamps the cita's `horario_id`/`doctor_id`/`hora_fin` from the chosen slot. It also rejects a second appointment for the **same patient + especialidad + servicio + date** when an existing cita there isn't `CANCELADA`/`NO_ASISTIO` (`pacienteYaTieneCita()`, checked early for a known patient and again inside the transaction). Time values are stored/compared as `H:i` (5-char) strings — MySQL coerces the `TIME` column, and availability code normalizes reads with `substr($t, 0, 5)` for SQLite. Date-range queries use `whereDate(...)` (not `whereBetween`) because the `date` cast writes `Y-m-d H:i:s` under SQLite.

**`CitaForm` renders two layouts of the same component, one page.** `components/citas.blade.php` is a shell (shared header + success/error banners) that `@include`s `components/citas/escritorio.blade.php` (full single-view form, wrapped `hidden lg:block`) and `components/citas/movil.blade.php` (4-step wizard: datos → especialidad/servicio → fecha/hora → confirmar, wrapped `lg:hidden`). The left marketing panel is `hidden lg:flex`. Both partials bind the same Livewire props; **mobile input `id`s are prefixed `m-`** so the two copies in the DOM don't collide. Wizard state lives in `CitaForm::$pasoActual` with `siguientePaso()` (validates only `CAMPOS_POR_PASO[$pasoActual]`), `pasoAnterior()`, `irAPaso()` (back-only); `reservar()` resets `$pasoActual` to 1. Desktop ignores `$pasoActual` entirely. If you add/rename a field, update it in **both** partials and in `CAMPOS_POR_PASO`. The form's `wire:submit.prevent="reservar"` means Livewire always intercepts the submit over AJAX — there used to be a plain-POST fallback (`HomeController::storeCita` / route `citas.store`) duplicating the same logic, but it was dead code (never reachable with JS enabled, which Livewire itself requires) and was removed; don't recreate that pattern. `HomeController::buscarPaciente` (GET `/pacientes/buscar`) is a separate JSON lookup endpoint used elsewhere.

**Admin panel** is a single `auth`-protected route group (prefix `admin`, name prefix `admin.`) using Laravel's default session guard — no roles/permissions layer, any authenticated `User` has full access. `Admin\CitaController` handles listing citas/pacientes and updating a cita's `estado`; `Admin\{Especialidad,Servicio,Doctor,Horario,Bloqueo}Controller@index` each host a Livewire CRUD manager (see the manager pattern above). Every admin view renders `<x-admin-nav />` at the top of its `@section('content')` — a tab bar (Citas, Pacientes, Especialidades, Servicios, Doctores, Horarios, Bloqueos) plus a "Cerrar sesión" POST form; active tab via `request()->routeIs('admin.<x>.*')`. Add a tab there when you add an admin section.

**All user-facing strings (validation messages, UI copy) are in Spanish.** Keep new copy consistent with this.

**Rate limiting**: named limiters `login` (5/min, keyed by email+IP) and `pacientes-buscar` (30/min by IP, since that endpoint returns a patient's name/phone/email by document number and is otherwise an enumeration vector) are registered in `RouteServiceProvider::boot()` and applied via `throttle:*` middleware in `routes/web.php`. `App\Livewire\CitaForm::reservar()` has its own manual `RateLimiter` check (5 submissions / 10 min by IP, counted only after validation passes so typos don't burn the budget) since Livewire component actions aren't reachable through `routes/web.php` middleware. Follow this same pattern (named limiter + `throttle:` middleware for plain routes, manual `RateLimiter::hit()`/`tooManyAttempts()` for Livewire actions) for any new public-facing endpoint that touches patient data or auth. Note: `pacientes.buscar` (`HomeController::buscarPaciente`) currently has no known frontend consumer — the plain-JS `fetch` that used to call it from `components/citas.blade.php` was removed (see below), since `CitaForm::buscarPaciente()` already does the same lookup natively. The route/controller/limiter were left in place rather than deleted, since removing an endpoint is a bigger call than fixing the bug at hand — but don't be surprised it's unreferenced.

**Never dispatch synthetic DOM events (`el.dispatchEvent(new Event('input'))`) on an input that has `wire:model`, to "clear" or "sync" it from plain JS.** This caused a real, user-reported bug: `components/citas.blade.php` used to run a second, independent patient-lookup implementation in a `<script>` tag (fetching `/pacientes/buscar` and writing directly into the `paciente_nombre`/`telefono`/`email` inputs, then firing synthetic `input` events so the visible value would "look" updated) — fully redundant with `CitaForm::buscarPaciente()`, which already runs server-side via `wire:change="buscarPaciente"` on tipo_documento and `wire:blur`/`wire:change`/`wire:keydown.enter` on numero_documento. Livewire can't distinguish a synthetic `input` event from a real keystroke: dispatching one on `telefono`/`paciente_nombre` while they were empty made Livewire treat them as user-edited-to-empty in the same request batch as the tipo_documento change, triggering `updated()` → `validateOnly()` on fields the user never touched — so selecting "DNI" alone showed "El telefono es obligatorio." before the user had done anything else. Fixed by deleting the whole duplicate script and the `#paciente-busqueda-result` div it drove (the equivalent `@if($pacienteEncontrado)` message already renders natively). If you need JS to react to a Livewire-bound field's value, do it through Livewire (`wire:model` + a PHP method, or `$wire` in Alpine/`@entangle`), not by writing to the DOM and re-dispatching input events.

**Admin pagination**: `Admin\CitaController::index()` renders `admin/citas/index.blade.php`, but the actual data comes from the `AdminCitas` Livewire component (`getCitasProperty()` → `Cita::...->paginate(15)`, using the `WithPagination` trait, `paginationTheme = 'tailwind'`, and `updatedFiltroEstado()` to reset to page 1 when the status filter changes) — the controller itself passes no data. `Admin\CitaController::pacientes()` paginates directly (`Paciente::orderBy('apellidos')->orderBy('nombres')->paginate(20)`). Both views render `{{ $x->links() }}` under the table. Follow this pattern (`paginate()` + `->links()`, `WithPagination` + page reset on filter change for Livewire-backed lists) for any new admin listing.

**Favicon**: `public/images/favicon.svg` is a cropped version of the brand mark (just the circular "C" + medical-cross icon from `logo-cori.svg`, square-ish viewBox, no wordmark) referenced via `<link rel="icon" type="image/svg+xml">` in the layout. `public/favicon.ico` is a legacy empty (0-byte) file — harmless since the explicit `<link rel="icon">` takes precedence in modern browsers, but don't rely on `favicon.ico` for anything.

**Footer / pre-footer CTA**: `layouts/app.blade.php` queries `ContentSection` directly (`contact_phone`/`contact_email`, same keys `App\Livewire\Contact` uses) to show real phone/email with icons in the footer's "Redes" column — this is a small duplicate read of the same data source, acceptable at this scale rather than introducing a shared view composer. The gradient CTA band ("Agenda tu cita en minutos") right before the footer is wrapped in `@unless(request()->is('login') || request()->is('admin/*'))` — it's a marketing element and shouldn't appear on internal/admin pages. If you add more admin routes outside `/admin/*`, extend that condition.

**Map placeholder**: the Google Maps iframe in `livewire/contact.blade.php` has `loading="lazy"` and can briefly show a blank white box. It's wrapped in `x-data="{ mapLoaded: false }"` with a pulsing skeleton (`x-show="!mapLoaded"`) that hides via `@load="mapLoaded = true"` on the iframe. Follow the same pattern for any other lazy-loaded iframe/embed.

**Admin login access**: `/login` had no discoverable entry point anywhere on the public site (only reachable by typing the URL). There are now three: a lock-icon link in the desktop header (next to the dark-mode toggle, before the "Reservar cita" CTA), a "Acceso administrativo" row in the mobile menu (visually separated from the page-section links with a border and muted color), and a small "Acceso administrativo" link in the footer's bottom bar next to the copyright. All three point to `route('login')`.

**WhatsApp**: the number (`51964278433`, i.e. +51 964 278 433) and the pre-filled `wa.me` message are hardcoded as `$whatsappNumber`/`$whatsappUrl` in the `@php` block near the footer in `layouts/app.blade.php` — not pulled from `ContentSection` (that model only has `contact_phone`, which is two landline-style numbers in one string, not a clean WhatsApp-ready number). Used in two places: a floating action button (fixed bottom-right, hidden on `/login` and `/admin/*` via the same `@unless` as the pre-footer CTA) and an icon in the footer's "Redes" row. If the WhatsApp number ever changes, it's only defined in that one place.

**Styling**: Tailwind CSS is compiled through Vite/PostCSS (`tailwind.config.js`, `postcss.config.js`, `resources/css/app.css`), loaded via `@vite(...)` in `layouts/app.blade.php`. All custom project CSS (`.section-reveal`, `.cori-input`, brand CSS variables, etc.) lives in `resources/css/app.css`, not inline in the layout. `public/build` is gitignored — **`npm run build` must be run and its output uploaded before every cPanel deploy**, or the site ships with no CSS/JS (Blade's `@vite` throws if the manifest is missing). Alpine.js is *not* loaded separately — Livewire 4 bundles its own Alpine instance via `@livewireScripts`; adding another Alpine `<script>` tag causes a "multiple instances of Alpine" console warning and undefined behavior.

**There is no Vite dev server running by default in this environment** — `public/build` is a static compiled snapshot. If you add or change any Tailwind class in a Blade/PHP file while `php artisan serve` is running without `npm run dev` alongside it, **you must run `npm run build` again** before checking the result in a browser, or the new classes simply won't exist in the served CSS (elements silently fall back to unstyled/black text, easy to misread as a different bug). Only colors/utilities actually used somewhere in `content` get compiled in — don't assume a class "should" work just because it's valid Tailwind.

**Section spacing on `home.blade.php`/`nosotros.blade.php` is self-contained per component** — each top-level `<section>` (or `livewire:` component's own root section) provides its own margin/padding (`mt-24`, or `py-14 md:py-20`). Don't add an extra `mt-*`/`pt-*`/`space-y-*` wrapper around a component that already spaces itself, or the gaps double up (this happened twice: `nosotros.blade.php` wrapped `components/nosotros` — which already opens with `mt-24` — in an extra `pt-24` div, and `home.blade.php` wrapped the services/ecografías/cirugías/especialidades cluster in `space-y-16` on top of each of those sections' own `py-14 md:py-20`). Both were fixed by removing the redundant wrapper spacing, not by shrinking the components' own margins.

**Admin panel styling** (`auth/login.blade.php`, `admin/*/index.blade.php`, `livewire/admin-citas.blade.php`, `livewire/admin/*-manager.blade.php`) uses the same design system as the public site: `.cori-input`/`.cori-label`/`.cori-error` for form fields, `bg-gradient-to-r from-brand-blue to-brand-pink` for primary buttons/table headers, `rounded-[2rem] ... shadow-card` white/slate-900 cards, and the pink "eyebrow" pill pattern for page headers. Status badges/action buttons use plain semantic Tailwind colors (`amber`/`emerald`/`rose`) rather than brand colors, since they're state indicators, not brand elements. Earlier versions of these views used undefined custom color classes (`text-primary-blue`, `bg-success`, `border-light-pink`, etc.) that were never in `tailwind.config.js` — they silently rendered as unstyled black-on-white and made the admin panel look broken; don't reintroduce color class names without checking they exist in the theme config.

**Per-page SEO**: `layouts/app.blade.php` builds `<title>`, `<meta name="description">`, canonical URL, Open Graph and Twitter Card tags from `@yield('title', ...)`/`@yield('description', ...)` with a site-wide fallback. Every view that `@extends('layouts.app')` should declare its own `@section('title', '...')` and `@section('description', '...')` right after the `@extends` line — otherwise it silently falls back to the generic site-wide copy (this was the case for every page until it was fixed). Admin/auth views should also set `@section('robots', 'noindex, nofollow')` (default is `index, follow`) since they're not meant to be indexed.

**Scroll-reveal animations**: sections with the `.section-reveal` class start at `opacity: 0` and are flipped to visible by an `IntersectionObserver` in `layouts/app.blade.php` (`threshold: 0`, plus a 4s `setTimeout` safety net that force-reveals everything). Keep the threshold low/permissive — a previous version used `threshold: 0.18`, which silently broke for any `.section-reveal` wrapper taller than the viewport (the required intersection ratio was never reached), leaving entire sections permanently invisible on the home and nosotros pages. If you wrap new content in `.section-reveal`, prefer wrapping smaller, viewport-sized chunks rather than one giant section spanning multiple unrelated blocks.

**Never put `.section-reveal` (or any class mutated by external JS) on the root element of an interactive Livewire component.** This caused a real bug: `components/citas.blade.php`'s root `<section id="citas" class="section-reveal ...">` *is* `App\Livewire\CitaForm`'s Livewire root. The `IntersectionObserver` adds `is-visible` to it client-side, but every Livewire update (e.g. `wire:change="buscarPaciente"` firing when the user picks "DNI") morphs that root element's attributes back to the server-rendered HTML — which never contains `is-visible` — snapping it back to `opacity: 0`. From the user's perspective the whole booking form vanished ("la pantalla se queda en blanco") the moment they touched the tipo_documento dropdown. Fixed by moving `section-reveal` onto a plain wrapper `<div>` *outside* the `@livewire(...)` call (in both `citas.blade.php` and `home.blade.php`), leaving the component's own root with only its layout classes — Livewire never touches elements outside its own root, so the wrapper's JS-added class is safe. If you add interactivity (`wire:model`/`wire:click`/etc.) to a component that currently has no reason to re-render, check whether its root — or an ancestor up to the nearest `wire:id` boundary — carries `.section-reveal` or any other class a script mutates outside Livewire's lifecycle.

**Test database**: `phpunit.xml` now sets `DB_CONNECTION=sqlite` / `DB_DATABASE=:memory:`, so `php artisan test` runs against a throwaway in-memory SQLite DB instead of the dev MySQL `clinic` database (which is what it used to hit — tests that touched the DB depended on it already being seeded). Feature tests that need tables use `RefreshDatabase`; `ExampleTest` calls `$this->seed()` because `GET /` renders DB-backed Livewire sections. Livewire manager/form tests live in `tests/Feature/AdminCrudTest.php` and `tests/Feature/CitaFormTest.php` and drive components via `Livewire::test(...)`.
